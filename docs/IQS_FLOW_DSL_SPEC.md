# IQS-Flow DSL 规范（企业体系文件流程图）

> **状态**: 设计定稿 v0（Design Draft，尚未实现）
> **版本**: 0.1.0
> **适用范围**: 新增 IQS-DSL v1 第 14 个 core kind —— `flow`
> **作者**: 洪光华 / 鹿溪联合创新实验室
> **落盘日期**: 2026-08-25

---

## 0. 背景与定位

信息中心日常管理 665 个体系文件，其中大量程序文件含"谁（泳道）× 做什么（活动）× 什么条件下走哪条路（网关）"的流程图需求。现有 13 个 core kind 中 **PDPC 与 arrow 是最相近的流程图形态**，但二者均**不支持泳道、无 BPMN 语义元素、无默认顺序流**，难以支撑体系文件的快速起草与全生命周期重构。

本规范定义第 14 个 core kind —— `flow`，一套**面向企业非技术员工、同时具备强机器可读性**的流程图 DSL，语义定界为 **BPMN 2.0 子集**，渲染**自研 SVG**（零新增第三方依赖）。

### 0.1 设计三原则

1. **默认顺序流**：同一泳道内按书写顺序自动连线，省去约 80% 的显式连线书写。
2. **泳道即节**：`Lane:` 开启一段，其下所有节点自动归属该泳道，归属直观。
3. **宽松输入 → 严格输出**：人写宽松语法，解析器归一为 **canonical JSON**（规范结构）；机器可读性不打折，`#id` 引用与稳定边 id 保障此点。

### 0.2 产品分层（沿用治理）

| 层级 | 语言 | 用途 |
|:---|:---|:---|
| **CORE** | IQS-Flow DSL（本 spec） | 体系文件流程图、成果报告、可审计、机器可读 |
| **RELIEF** | Mermaid | 仅类型外制图；`flow` 已覆盖不可用 Mermaid 充当终稿 |

### 0.3 三层机器输出

解析器产出三种可消费形态：

| 输出 | 用途 |
|:---|:---|
| **canonical JSON** | 校验、图谱抽取、版本 diff、跨文档审计 |
| **BPMN 2.0 XML** | 可导入第三方 BPMN 专业工具（bpmn-js / Camunda 等）交换 |
| **自研 SVG** | 渲染与终端展示 |

## 1. 语义子集定界（BPMN 2.0 子集）

面向企业体系文件，仅保留四大类共 **8 种节点 + 3 种连线 + 3 种修饰**（BPMN 100+ 元素中不出现的边界事件、补偿、多实例、消息/定时/信号事件一律裁剪；保留**子流程**以满足"程序文件互相引用"的刚需）。

| 大类 | 元素 | 主标记 | 定位 |
|:---|:---|:---|:---|
| **事件** | 开始 | `[S]` | 唯一开始点 |
| | 结束 | `[E]` | 流程终结 |
| **活动** | 任务 | （省略） | 圆角矩形，默认元素 |
| | 子流程 | `[SUB]` | 圆角矩形＋，可内嵌一层子图 |
| **网关** | 排他 | `[?]` | 判断分叉（菱形） |
| | 并行 | `[+]` | 会签/并发（菱形＋） |
| **修饰** | 文本标注 | `[N]` | 挂要点说明 |
| | 数据对象 | `[D]` | 记录/表单（纸带形） |

**连线**：

| 连线 | 视觉 | 用途 |
|:---|:---|:---|
| 序列流 | 实线箭头 | 主流程流转（隐式自动连 + 显式补充） |
| 消息流 | 虚线箭头 | 跨泳池传递（v0 预留，暂不强制） |
| 关联 | 点线 | 修饰物挂接到节点（Annotation/DataObject） |

**布局**：`Layout: H`（横向泳道 = 泳道自上而下排列，默认）/ `Layout: V`（纵向泳道 = 泳道自左而右排列）。

## 2. 元素标记表

单字母主标记优先（全键盘可输入、无 Unicode 编码坑），解析器**全兼容**中英别名。

| 元素 | 主标记 | 兼容别名 | BPMN 视觉 |
|:---|:---|:---|:---|
| 开始 | `[S]` | `start` `开始` `[*]` | ○ 细圆 |
| 结束 | `[E]` | `end` `结束` `[#]` | ● 粗圆 |
| 任务 | **省略** | `[T]` `task` `任务` | 圆角矩形 |
| 判断 | `[?]` | `[G]` `gateway` `判断` | ◇ 菱形 |
| 并行 | `[+]` | `[P]` `parallel` `并行` | ◇＋ |
| 子流程 | `[SUB]` | `[@]` `subprocess` `子流程` | 圆角矩形＋ |
| 文本标注 | `[N]` | `note` `注` | 折角纸 |
| 数据对象 | `[D]` | `data` `数据` | 纸带 |

> **标记放置**: 标记置于节点行首，格式 `id <标记> 标签`。如 `s3 [?] 金额超过5000?`。
> **可省略性**: 任务标记**可省略**，无标记行默认判为任务；节点 id **也可省略**，由解析器按 `lane序号-节点序号` 自动分配并回填 canonical JSON。

## 3. DSL 语法定稿

### 3.1 全局外壳

| 指令 | 示例 | 说明 |
|:---|:---|:---|
| `Title:` | `Title: 采购申请审批流程` | 图表标题 |
| `Layout:` | `Layout: H` | H(默认)/V，兼容 horizontal/vertical/横向/纵向 |
| `//` | `// 注释` | 行注释 |

### 3.2 泳道

```dsl
Lane: 申请人        // 开启一段泳道，其后节点自动归属
Lane: 财务, 见票付款   // 泳道名 + 可选说明
Pool: 采购部         // 可选泳池包裹（多个泳道归入一个泳池），v0 可选
```

### 3.3 节点行

```
<id> <标记> <标签>
```

- `id`：可选，全局唯一；缺省自动分配。
- `标记`：任务可省略，其它元素必须其一。
- `标签`：中文描述。标签内避免半角逗号/分号（复用 v1 全角标点约定）。

### 3.4 分支行（判断/并行的出口顶点）

```
<标签> <(出口标记)> [<条件>] → <目标>
```

| 部分 | 语法 | 说明 |
|:---|:---|:---|
| 标签 | `是` `否` `通过` `报废`… | 任意文本，作为连线标签 |
| 出口标记 | `(pass)` | **可选命名**，使该边获得稳定 id，可跨文档引用与审计；缺省自动编号 |
| 条件 | `[金额>5000]` | 可选，BPMN conditionExpression，输出到 JSON `condition` 字段 |
| 目标 | `→ #b1` | **强制 `#id`**；可省略 = 接本泳道下一顺序节点；可多目标 `→ #w2, #w4`（自动拆并行边） |

**四档弹性**：

| 档位 | 语法 | 说明 |
|:---|:---|:---|
| ① 命名出口 | `合格 (pass) → #w1` | 边 id 稳定 = `pass` |
| ② 带条件 | `返工 (rework) [缺陷≤3] → #q3` | 输出 condition 字段 |
| ③ 默认出口 | `否则 → #w3` | BPMN default flow，渲染实线带斜杠 |
| ④ 多目标扇出 | `报废 → #w2, #w4` | 自动拆两条并行边，语义等价并行网关 |

**约定**：多条分支指向同一节点 = 隐式合并（BPMN merge），无需额外语法。

### 3.5 内嵌子图（子流程）

```dsl
[SUB] 按《合同评审程序》执行
  c1 [S] 初审
  c2 [?] 合规?
    是 → #c3
    否 → #s2
  c3 [E] 盖章
```
子流程内嵌节点自动成为子图；**支持一层嵌套**（体系文件场景一层足够，递归展开留待后续）。

## 4. 完整示例

### 4.1 横泳道 + 分支（典型审批流程）

```dsl
Title: 采购申请审批流程
Layout: H

Lane: 申请人
  s1 [S] 提交采购申请
  s2 填写申请单
  s3 [?] 金额超过5000?
    是 → #b1
    否 → #s4
  s4 直接执行
  s5 [E] 归档

Lane: 部门经理
  b1 审批
  b2 [?] 是否通过?
    是 → #f1
    否 → #b3
  b3 退回修改
  b3 → #s2            // 显式回边

Lane: 财务
  f1 付款
  f2 [E] 完成
```

### 4.2 纵泳道 + 多出口分支

```dsl
Title: 来料质检
Layout: V

Lane: 质检
  q1 [S] 来料检验
  q2 [?] 检验结果?
    合格 (pass) → #w1
    返工 (rework) [缺陷≤3] → #q3
    否则 → #w3
    报废 → #w2, #w4
  q3 返工处理
  q3 → #q1

Lane: 仓库
  w1 入库
  w4 报废登记
Lane: 采购
  w2 联系供应商换货
  w3 让步接收
```

### 4.3 内嵌子流程

```dsl
Title: 合同评审
Lane: 采购
  a1 [S] 提交合同
  a2 [SUB] 按《合同评审程序》执行
    c1 [S] 初审
    c2 [?] 合规?
      是 → #c3
      否 → #a4
    c3 [E] 盖章
  a3 归档
  a4 [E] 驳回
Lane: 法务
  l1 法律审查
  l1 → #a2
```

## 5. canonical JSON（机器可读输出）

```json
{
  "kind": "flow",
  "title": "采购申请审批流程",
  "layout": "horizontal",
  "pools": [{"id": "P1", "name": "采购部"}],
  "lanes": [
    {"id": "L1", "name": "申请人", "pool": null},
    {"id": "L2", "name": "部门经理", "pool": null},
    {"id": "L3", "name": "财务", "pool": null}
  ],
  "nodes": [
    {"id": "s1", "type": "start", "label": "提交采购申请", "lane": "L1"},
    {"id": "s2", "type": "task", "label": "填写申请单", "lane": "L1"},
    {"id": "s3", "type": "exclusiveGateway", "label": "金额超过5000?", "lane": "L1"}
  ],
  "edges": [
    {"id": "pass", "from": "q2", "to": "w1", "type": "sequence", "label": "合格", "condition": null, "default": false},
    {"id": "rework", "from": "q2", "to": "q3", "type": "sequence", "label": "返工", "condition": "缺陷≤3", "default": false},
    {"id": "q2-D", "from": "q2", "to": "w3", "type": "sequence", "label": "否则", "condition": null, "default": true},
    {"id": "q2-4a", "from": "q2", "to": "w2", "type": "sequence", "label": "报废", "condition": null, "default": false},
    {"id": "q2-4b", "from": "q2", "to": "w4", "type": "sequence", "label": "报废", "condition": null, "default": false}
  ],
  "artifact": [
    {"id": "n1", "type": "annotation", "label": "依据《XX制度》", "attach": "s2"}
  ],
  "subProcesses": [
    {"id": "a2", "nodes": ["c1", "c2", "c3"]}
  ]
}
```

**边 id 规则**：显式 `(out)` 用该名；缺省自动编号为 `<源id>-<出口序>`（`s3-N`）或 `<源id>-<档位><序>`（多目标 `q2-4a`）。

## 6. 内置校验（Relaxed-in, Strict-out 的兑现）

| 校验项 | 规则 |
|:---|:---|
| 开始点 | 全局仅一个 `start`；结束至少一个 `end` |
| 节点引用 | 所有 `#id` 目标必须存在 |
| 泳道引用 | 节点引用的 lane 必须已定义 |
| 网关出入度 | 排他/并行：1 入 ≥1 出；默认出口仅一个 |
| 孤立节点 | 无孤立节点（除开始/结束外的节点至少 1 入 1 出） |
| 分支合法性 | 分支行只能出现在网关/并行节点之后 |
| 子图边界 | 子流程内嵌一层，不递归穿越 |

校验失败时返回短错误 + 骨架回执（沿用治理 §4 策略）。

## 7. 落地路径（对齐现有治理，零新依赖）

按现有 IQS 规范治理新增 core kind 的标准流程：

1. **注册**：`dsl/kinds.json` 新增 `flow` 条目（`tier: core`、`family: iqs_native`、`body: FlowGraph`、`mcpName: render_flow`、colorSlots）。
2. **组件**：`components/FlowEditor.tsx`（宽松解析 → canonical）+ `components/FlowDiagram.tsx`（**自研 SVG**：泳道网格 + 正交连线 + 自动布局）。
3. **协议切片**：新增 `protocol/segments/flow.md`（Soul / Grammar / Seed 三段式，对齐 mermaid.md / pdpc.md）。
4. **MCP**：发布 `render_flow`（瘦描述 + intents + resource URI）。
5. **校验集成**：解析器 + validator + `npm run validate:dsl`。
6. **文档闭环**：本 SPEC 升版至 1.0 并登记进 `protocol/DSL_V1.md` 权威文档链。

### 变更流程（沿用治理 §5）

改语法 → 先升本 SPEC 版本 → 改 `kinds.json` → 改 `FlowEditor` 解析器 → 改 MCP example → `npm run validate:dsl` 全量校验。

## 8. 与现有 kind 的关系

| 既有 kind | 与本 flow 的关系 |
|:---|:---|
| `pdpc`（过程决策程序图） | 两者语义不同：PDPC 面向**风险对策推演**（防错树），flow 面向**岗位×活动流程**（泳道序列）。不得互相替代。 |
| `arrow`（箭头/因果链） | arrow 是单向因果链，无泳道无网关；flow 是完整流程建模。互补不重叠。 |
| `mermaid`（救济） | flow 已覆盖流程建模时，禁止用 Mermaid flowchart 充当成果终稿（治理红线 2/3）。 |
